How to Track Token Usage Without Collecting Prompts: Tool Switches, Counts-Only Mode and Optional Reads

Kite Pulse teamUpdated 2 Nov 20267 min read

You can track token usage without collecting prompts by counting tokens on each developer's computer and sending only the numbers, so the conversation never leaves the machine. Token counts answer the volume questions (how much AI, on which tools) without any of the text.

Collection is then a decision an admin makes three times: which tools are read at all, which of those send conversations or counts only, and which extra reads, if any, are switched on.

Three levels of collection, chosen per tool

Before looking at any product screen, it helps to name the options. For each AI coding tool a team uses, there are three sensible settings, and the right one depends on the question you need answered.

SettingWhat leaves the computerWhat it answersFits when
OffNothing from that toolNothing about that toolThe tool is not used, or not approved
Counts onlyToken numbersHow much each tool is used, and by whomYou need volume and adoption figures, and agreed not to hold the text
Full session syncThe tool's conversation, with secrets maskedVolume plus what the sessions did: commands, failures, projects, work patternsTeams want the session views, and developers have agreed to it

Most privacy disagreements about AI usage data are really disagreements about which row a tool belongs in. Writing the table down per tool, before anything is installed, turns a vague worry into a short list of choices people can sign off.

Tool switches: which tools are read at all

Kite Pulse reads the session history of ten AI coding tools: Claude Code, Codex, Gemini CLI, Cursor, GitHub Copilot Chat in VS Code, Cline, Roo Code, Kilo Code, OpenCode and Aider. All ten are on in a new install. An admin can switch any of them off on the Tools page, and desktop apps pick the change up at their next check-in.

Two points are worth checking before you decide. First, what each tool records differs: Cursor and Copilot Chat give input and output tokens only, for example, and the integration pages list what each of the ten tools provides. Second, for Copilot only the Chat in VS Code is read; inline completions, JetBrains and Copilot CLI are not collected, so switching Copilot on does not cover them.

Projects have their own switch. Projects an admin switches off are not read at all, which is the right control for a client repository or a confidential piece of work that should stay out entirely.

Counts-only mode in practice

The Tools page has two switches per tool: Session sync, which uploads the conversations, and Token consumption, which counts tokens. With Session sync off and Token consumption on, the desktop program counts tokens on the computer and sends only the numbers, never the conversation. Those small status records travel over HTTPS to the server your team runs.

What you give up is everything built from the conversation itself. For a tool in counts-only mode there is no session text to read, so views that depend on what the session did, such as failed commands and repeated retries, have nothing to work from for that tool. That is the trade, and it is a fair one when the question is volume.

Illustrative example, not a customer case

A company's works council asks that no prompt text leave developers' laptops during a three-month trial. The admin sets every tool to counts only. Finance gets token use per tool from the start. After the trial, the council agrees full session sync for the two tools most of the team uses, and those two switches change; the others stay on counts only.

Starting narrow and widening by agreement tends to go better than the reverse. Our post on developer analytics without keystroke tracking covers why developers push back on collection they were not asked about.

Optional reads: off until an admin turns them on

Beyond the session history, the desktop program can read a few extra things. Every one of them ships switched off, and they are all switched on in one place: Settings › Retention › Kite Pulse app reads. Each shows the app version it needs (0.4.2 unless noted), and each appears on every developer's Privacy page, so people can see which are on.

The two reads to discuss before switching on are frameworks and project notes. By default the program does not open a project's source files; these two open specific files in the project, and project notes can describe a lot about how a codebase works. Privacy preserving analytics: what holds whatever you choose

Privacy preserving analytics depends as much on the defaults you cannot switch off as on the switches. These hold at every setting:

Always in place

  • No session content uploads until the developer confirms their projects, and an approver signs off where required
  • Secrets masked on the computer and again on the server
  • Session uploads encrypted before they leave the computer
  • Data goes only to the server your team runs
  • Tool accounts pseudonymised by default: a keyed hash, the email domain and the plan name, never the address

Never done

  • Logging keystrokes
  • Taking screenshots
  • Tracking websites
  • Opening a project's source files (the optional reads above aside)

That last line is why pseudonymised developer analytics and developer analytics without source code access are both possible here, with one caveat to state plainly: full session records can include excerpts of code the AI read or wrote. Counts-only mode removes that caveat for a tool. For the detail of what is read, why and what is sent, see the privacy page; for sign-in, roles and the audit log, see security. The source-code question has its own post: developer analytics without source code access.

When another approach fits better

  • One tool, totals only. If the team uses a single AI vendor and you only need its usage totals, that vendor's own admin console may be enough.
  • Delivery metrics. For lead time and deployment figures from git and tickets, a git or ticket based tool fits better. Session data does not replace it.
  • No code excerpt may leave a laptop, ever. Full session sync does not meet that rule. Counts-only mode does, with token figures only.
  • Tools outside the ten. Nothing outside the ten supported tools is read.

Questions about collecting less

Can I track AI coding usage without reading developers' prompts?

Yes. Token counts answer how much AI is used, on which tools, without any conversation. In Kite Pulse, an admin turns Session sync off and Token consumption on for a tool; the desktop program then counts tokens on the computer and sends only the numbers. You give up the views that are built from the conversation itself for that tool.

Does the tool collect source code, prompts, or other sensitive developer information?

It depends on the mode you choose per tool. With full session sync, Kite Pulse uploads the AI tool's conversation, which includes prompts and can include excerpts of code the AI read or wrote, with secrets masked on the computer and again on the server. In counts-only mode only token numbers are sent. It does not open a project's source files, log keystrokes, take screenshots or track websites, and the optional reads of project notes and package manifests stay off until an admin turns them on.

How do I track AI coding usage without monitoring keystrokes?

Read the session history the AI coding tools already keep on each computer instead of watching the keyboard or screen. Those records hold token counts and, if you choose, the conversation itself. Kite Pulse reads them for ten tools, sends only new activity to a server your team runs, and lets an admin limit any tool to token counts only.
