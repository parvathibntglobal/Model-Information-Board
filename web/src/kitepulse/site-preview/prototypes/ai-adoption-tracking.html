AI Adoption Tracking: See Which AI Tools and Models Your Company Really Uses

Kite Pulse teamUpdated 30 Oct 20268 min read

AI adoption tracking means counting how AI coding assistants are actually used: which tools and models, by how many developers, on which projects, and how that changes over time. The reliable source is the session history the tools already keep on each developer's computer, not licence counts or surveys. Read that history consistently across tools and you get adoption figures leaders can compare period to period.

Why licence counts are not adoption

Most companies know how many AI seats they pay for. Fewer know how many of those seats are in daily use, which models people choose when they have a choice, or which projects get most of the AI work. A seat bought in January says nothing about whether it was used in June.

Executives and technology leaders usually want three answers. Which AI tools and models are really used? Is use growing, flat or falling? And which projects depend on AI enough that a change in tool, model or plan would be felt? Each of those needs a count of real activity, taken the same way every week.

There is a second reason to measure use directly. Developers often run more than one assistant: a terminal agent for larger changes, an editor extension for quick questions, a different model for a different job. Any single vendor's view shows one slice of that, and the slices do not add up on their own.

AI adoption metrics worth tracking

Good AI adoption metrics are counts you can check, broken down the way decisions are made. A practical set for AI coding assistant adoption:

MetricWhat it tells you
Developers per toolHow widely each assistant is used, and whether a tool you pay for has few active users.
Developers per modelWhich models people choose, and how quickly a new model is picked up.
Token use per tool, model and projectWhere the volume of AI work is, which is often different from where the headcount is.
Sessions and active timeWhether use is a daily habit or an occasional experiment.
Accounts per toolWhether people work under company accounts, and whether one login is shared by several people.
The same figures over timeThe trend. A single month is a snapshot; adoption is a direction.

Two habits keep these honest. Compare each period with the one before rather than reading a single number on its own, and keep the breakdowns at team and project level when the question is about the organisation. Adoption is a property of how a company works, and it is best read that way.

Four ways to measure AI coding assistant adoption

Quick

Surveys

Easy to run and good for sentiment. Weak for counts: people misremember how often they used a tool, and the answers cannot be repeated exactly next quarter.

Per vendor

Vendor admin consoles

Accurate for that vendor's own tool, as far as each console goes. Each one usually covers a single tool, so a team using several assistants gets several partial views in different formats.

Delivery

Git and ticket analytics

Show what was shipped, and the right choice for delivery metrics. They cannot see the AI conversation itself, so they do not say which tool or model did the work.

Sessions

Session history

Reads the records the AI tools already keep on each computer. Covers several tools in one consistent format, down to model and project, with nothing for developers to log.

These are not exclusive. Many teams pair a session view of AI use with their existing engineering analytics for delivery and planning, because each answers questions the other cannot.

AI model adoption tracking

AI model adoption tracking answers a narrower question: when a new model arrives, who moves to it and how fast, and which projects still rely on an older one. That matters for plan choices and for knowing where a model change would land.

The Models tab answers it from the model name each session records. Most of the ten tools record it. Two are partial: Cursor gives a model name only when one model served the whole chat, and GitHub Copilot Chat in VS Code only when it was recorded. Read the Models tab as complete for the other eight tools and partial for those two.

Model use and cost are separate questions. Estimated cost is shown per tool, from published list prices, and labelled "not billed spend". Claude and Gemini models are priced, and Aider, Cline, Roo Code, Kilo Code and OpenCode report their own cost; Codex, Cursor and Copilot usually show a dash rather than a figure. What this view of adoption does not show

What it counts

  • Sessions, tokens and models from the ten supported tools
  • Which project each session belongs to
  • Accounts each tool runs under, for five of the tools
  • The same figures for any period, compared with the previous one

What it does not count

  • AI tools outside the ten, or tools an admin has switched off
  • Copilot inline completions, Copilot in JetBrains and Copilot CLI
  • Activity from developers who have not confirmed their projects
  • Whether the AI-written code was good: it is not a code-quality tool

Reporting adoption to leadership

Adoption figures are most useful on a schedule. The company report covers any period and compares it with the previous one, and it downloads as CSV or PDF, by admins by default. Admins can also email it daily, weekly or monthly as a scheduled report, once email is set up on the server. A quarterly review then starts from the same counts every time, rather than from a fresh survey.

Questions about AI adoption tracking

How do I measure AI coding tool adoption on my team?

Count from what the tools record, not from licences or surveys. Track how many developers used each tool and each model in a period, their token use, which projects the sessions belonged to, and how those figures move week by week. A tool that reads the session history AI coding assistants already keep, such as Kite Pulse, gives you those counts without anyone logging their own use.

How has AI coding-tool adoption changed over time?

For your own company, the answer is in your own data, not in an industry average. Plot developers per tool and per model, and token use, over months, and compare each period with the one before. In Kite Pulse, the Models tab of Team AI Usage shows model adoption over time, and the company report compares any period with the previous one.

Can I see which AI models are being used and how frequently?

Yes, for the tools that record a model name. Kite Pulse's Team AI Usage shows token use per model for any period, and its Models tab shows how many developers use each model and how that changes over time. Most of the ten supported tools record the model; Cursor does so only when one model served the whole chat, and GitHub Copilot Chat in VS Code only when it was recorded.

How do I find out which projects my team uses AI on the most?

Link every AI session to the repository it ran in, then count tokens and sessions per project. Kite Pulse does the linking automatically from folders and repository addresses, so one repository cloned on several machines counts as one project. Team AI Usage has a Projects tab, the Models tab shows models by project, and All Projects lists sessions and contributors per project.
