Token Usage per Developer: Tokens by Person, Tool, Model, Project and Day

Kite Pulse teamUpdated 30 Oct 20268 min read

Token usage per developer is the number of tokens each person's AI coding sessions sent and received, split by tool, model, project and day. Most teams cannot see it in one place, because each AI vendor's console covers only its own tool. Read the counts as a description of how AI is used across the team, and pair them with the model, the project and the kind of work before drawing any conclusion about a person.

Why per-developer token counts are hard to get

A token is the unit AI tools use to measure the text sent to a model and the text it sends back. It is also the basis of AI cost, so it is the first figure finance and engineering leaders ask for. The trouble is where the numbers live.

Each AI coding tool keeps its own history on each developer's computer, in its own format. A vendor's admin console, where there is one, shows usage for that vendor's tool only. A developer who uses Claude Code in the morning and Cursor in the afternoon appears in two places, under two accounts, with no shared project name. Many people are also on flat subscriptions, so the invoice says little about who used what.

To track LLM token usage by team across several tools, you need the counts gathered from every tool, joined to the right person and project, and kept in one consistent format.

Where the token counts come from

Kite Pulse does not ask developers to log anything. A small desktop program on each computer (Windows or macOS) reads the session history ten AI coding tools already keep: Claude Code, Codex, Gemini CLI, Cursor, GitHub Copilot Chat in VS Code, Cline, Roo Code, Kilo Code, OpenCode and Aider. It masks secrets, encrypts session uploads and sends only new activity to a server your team runs, after the developer confirms their projects.

Not every tool records the same detail, and the figures are only as complete as the tool's own records:

Token usage by model and AI model adoption tracking

Model choice shapes both cost and results, and teams drift between models as vendors release new ones. Token usage by model tells you which models carry the work today. Adoption over time tells you how quickly a new model is picked up, and whether an older one is still in use somewhere.

On the Models tab of Team AI Usage you see:

  • Developers per model, so you know how many people use each one.
  • Model adoption over time.
  • Models by project, so you can see which projects rely on which models.
  • Claude Code effort-level and speed settings.

The model name comes from each session's own record. Where a tool does not record it, as with Cursor chats that switched models, those tokens cannot be filed under a model, so read the Models tab together with the table above.

Claude Code agent features usage

Two developers can use a similar number of tokens in very different ways. One runs single conversations; another starts sub-agents, runs commands in the background and works across several worktrees at once. The Agent features tab shows which Claude Code agent features sessions used, such as sub-agents, background commands, plan mode, worktrees and MCP tools, by session and by developer.

This is often the context a per-developer token count is missing. Higher use can simply mean more agent work running in parallel. To see how many AI agents and sub-agents a person has working at once, and a lane chart for any past day, see Agents in parallel on The Office page.

From tokens to estimated cost

Tokens are counted; cost is estimated. Kite Pulse multiplies tokens by each vendor's published list price, keeping older sessions at the price they ran at. Claude and Gemini models are priced, and Aider, Cline, Roo Code, Kilo Code and OpenCode use the cost the tool reports itself. Codex, Cursor and Copilot usually show a dash, never $0.

  • On Team AI Usage, cost is shown per tool, labelled "not billed spend", and never added up across tools.
  • Cost per developer is shown to admins only, on that developer's AI Usage tab.
  • Per team or project, cost appears in AI Budgets: a monthly budget in tokens or estimated US dollars, with alerts at 80% and 100%. A dollar budget adds up the priced tools and reports unpriced tokens separately.

For a step-by-step method, including what to do about tools with no price, see the guide to tracking AI coding costs.

Reading per-person token figures as usage

A token count describes how much AI a person used. It does not say how much they delivered, how good the work was, or how hard the problem was. A developer debugging a large legacy service may send far more context than one writing a small new module, and both may be doing exactly the right thing. Tool and model matter too: the same task can cost very different token counts in two tools.

Good uses of per-developer tokens

  • Matching plans and seats to how people actually work
  • Spotting an unusual day and asking what happened
  • Seeing which models and tools a team has adopted
  • Setting budgets per team or project

Weak uses

  • Treating more tokens as more output
  • Treating fewer tokens as more efficient work
  • Comparing people on different tools or models
  • Judging a person on one number without the project and work behind it

Some ordering of people is useful. Plan headroom lists who is close to a Claude plan limit, worst first, across the 5-hour, weekly and per-model weekly windows, so a lead can move work before someone hits the limit. It covers Claude Code only. For the wider picture of how AI-assisted work happens, beyond tokens, see AI coding analytics for teams.

When another approach fits better

  • One tool only. If the whole team uses a single AI tool, that vendor's own admin console may already show enough usage detail.
  • Exact billing. For the amount you will actually pay, use the vendor's invoice. Kite Pulse cost figures are list-price estimates.
  • Delivery metrics. For lead time or deployment frequency from git and tickets, a git-based analytics tool is the better fit.

Kite Pulse fits when several AI coding tools are in use and you want token use per developer, model and project in one place, without sending data to a vendor cloud.

Questions about token usage per developer

How can I see how many tokens each developer uses?

Each AI vendor's console shows token use for its own tool only, so a team on several tools has to combine the numbers. Kite Pulse reads the token counts ten AI coding tools already record on each developer's computer and shows them on Team AI Usage per developer, tool, model, project and day, for any period. Managers see their own reporting line and admins see everyone.

How can I track which AI models (Opus, Sonnet, GPT) my team uses?

Use the model name each session records. On Kite Pulse's Models tab you see developers per model, model adoption over time and models by project, plus Claude Code effort-level and speed settings. Most of the ten supported tools record the model; Cursor does so only when one model served the whole chat, and GitHub Copilot Chat in VS Code when it is recorded.

Can I see which AI models are being used and how frequently?

Yes. Team AI Usage shows token use per model for any period, and the Models tab shows how many developers use each model and how that changes over time. Frequency is measured in tokens and developers, from the sessions the tools recorded, so a model used in a tool that does not record its model name will not appear under that model.
