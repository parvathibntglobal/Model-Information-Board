Claude MD Version Control: Keeping CLAUDE.md and AGENTS.md in Git

Kite Pulse teamUpdated 2 Nov 20268 min read

Claude MD version control means committing your project's CLAUDE.md (and AGENTS.md, if you use it) to the repository and changing it through reviewed commits, like any other file that shapes how the software is built. Shared rules go in the committed file, personal preferences go in a local file that git ignores, and every change carries a reason. Then git log and git blame can tell anyone why the agent behaves the way it does.

Why your agent instructions belong in version control

A CLAUDE.md file is read at the start of every Claude Code session in that project. Whatever it says about build commands, test habits, folders to avoid or how to write a migration, the agent will try to follow. In practice that makes it configuration for how code gets written, and configuration that lives outside version control drifts.

Three things go wrong when the file is treated as a scratchpad. Rules appear with no reason attached, so nobody dares remove them later. Rules disappear in an unrelated commit, and the mistake they prevented comes back. And each developer's copy slowly diverges, so two people running the same agent on the same repository get different behaviour without knowing why.

Keeping the file in git, and changing it on purpose, fixes all three. It also gives you a record of how your team's working practices changed as you learned what the agents get wrong, which is part of a project's institutional knowledge and usually the hardest part to reconstruct later.

What to commit and what to keep local

Claude Code reads instruction files at several levels, and only some of them belong in the repository. Anthropic's documentation describes these locations:

FileWho it applies toCommit it?
./CLAUDE.md or ./.claude/CLAUDE.mdEveryone working in the projectYes. This is the shared file.
CLAUDE.md in a subfolderWork in that part of the codebase; loaded when the agent works thereYes, with the code it describes.
.claude/rules/*.mdRules split by topic, or scoped to certain file pathsYes.
./CLAUDE.local.mdOnly you, in this projectNo. Add it to .gitignore.
~/.claude/CLAUDE.mdOnly you, in every projectNot in the project repository.
Managed policy CLAUDE.mdEveryone in the organisation, placed by ITIn whatever repository IT uses to distribute it.

Two details matter for review. Files found from the project folder upward are combined, not overridden, so a short project file plus a short subfolder file is easier to reason about than one long file. And a CLAUDE.md can pull in another file with an @path import, which helps you organise a long file but does not make it cheaper: imported files load together with the file that imports them.

AGENTS.md vs CLAUDE.md

AGENTS.md is an open format for instructions to coding agents, described by its maintainers as a README for agents. Many tools read it, including Codex, Cursor, Gemini CLI, Aider, Roo Code, Kilo Code and OpenCode. In a monorepo you can place one in each subproject, and the nearest file to the work takes precedence. CLAUDE.md is the file Claude Code reads.

Recent Claude Code versions can also read AGENTS.md, with one catch that is easy to trip over. By default Claude reads AGENTS.md only when there is no CLAUDE.md, .claude/CLAUDE.md or CLAUDE.local.md in the working folder or above it. So a developer who adds a private CLAUDE.local.md to a project that relies on AGENTS.md quietly stops getting the shared instructions.

One tool

CLAUDE.md only

Fine when the whole team uses Claude Code. Simplest to review.

Several tools

AGENTS.md as the source

Write the shared rules once in AGENTS.md, and keep a short CLAUDE.md that imports it with @AGENTS.md plus any Claude-only notes. One file to review, every tool reads the same rules.

Avoid

Two full copies

Two files saying nearly the same thing drift within weeks, and reviewers end up approving a change in one and missing the other.

CLAUDE.md best practices for a shared repository

These work equally well as AGENTS.md best practices. Most of them are ordinary good habits for any configuration file, applied to one that people tend to edit in a hurry.

  • Review it like code. Changes to the shared file go through a pull request. If your platform supports code owners, name one or two people for the instruction files so a change always reaches someone who knows why the existing rules are there.
  • Put the reason next to the rule. One line is enough: what went wrong, and roughly when. A rule with its reason can be judged later; a bare rule can only be obeyed or deleted.
  • Write commit messages for the next reader. "Update CLAUDE.md" tells nobody anything. "Stop the agent running migrations against the shared database" does.
  • Keep it short. Anthropic suggests aiming for under 200 lines per CLAUDE.md, because longer files take more context and are followed less consistently. Move rules that only matter for one area into a subfolder file or a path-scoped rule.
  • Keep secrets and personal paths out. Sandbox addresses, your own test data and anything resembling a credential belong in the ignored local file or nowhere.
  • Instructions guide; they do not enforce. The agent treats these files as context. When something must never happen, use a hook or a permission setting as well, and keep the CLAUDE.md line as the explanation.
  • Link decisions instead of pasting them. If the team keeps decision records, point to the record from the rule. The decision stays in one place and the instruction stays short.

An illustrative example, not a customer case. A team adds "never edit generated API clients by hand" after an agent's change is overwritten by the next build. Months later, a newer team member trims the file and removes the line as noise. With the reason written beside the rule and the change in a reviewed pull request, the reviewer sees what is being dropped and asks. Without them, the same mistake waits to happen again.

Reading the CLAUDE.md change history

Once the file is versioned, the CLAUDE.md change history answers most "why does the agent do this?" questions with plain git:

git log --follow -p -- CLAUDE.md      every change, with the diff
git blame CLAUDE.md                   who last changed each line, and in which commit
git log -S "migrations" -- CLAUDE.md  when a phrase was added or removed
git log -p -- AGENTS.md .claude/rules  the same for the other instruction files

The -S search is the useful one when a rule has gone missing: it finds the commit that removed the text, even if the file was rewritten since. Pair it with the pull request for that commit and you usually have the reason.

What git cannot show is how the instructions met the work. It records that a rule changed, not which sessions ran under the old version or whether the agent kept tripping over the same problem afterwards. That part of the picture comes from the sessions themselves.

Keeping instructions consistent across many repositories

A single project is easy. Thirty repositories, each with its own file, is where shared practice starts to fork. The usual options, and where each fits:

ApproachFits whenWatch out for
Per repository fileProjects really differ in how they build and testCompany-wide rules copied by hand and drifting
Template repositoryNew projects should start from one agreed fileOnly helps at creation; old projects keep the old text
Managed policy fileA few rules must apply to every developer's Claude CodeChanges go through IT's distribution, not a project pull request
Shared skills and commandsA workflow repeats across teamsNeeds an owner, or stale skills pile up

Most teams combine them: a short managed file for the handful of rules that apply everywhere, a committed file per project for local detail, and reusable skills for the repeated workflows.

Questions about versioning agent instructions

How do I share AI best practices across my team?

Write them where the agents read them: a project CLAUDE.md or AGENTS.md committed to the repository, reviewed in pull requests like any other change, with one line saying why each rule exists. Keep personal preferences in an ignored local file, and put company-wide rules in one shared place rather than copying them into every repository. When a workflow keeps repeating, turn it into a reusable skill or command instead of another paragraph of instructions.
