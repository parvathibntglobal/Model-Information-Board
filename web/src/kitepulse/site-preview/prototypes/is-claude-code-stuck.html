How to Tell if Claude Code Is Stuck, or Only Waiting for You

Kite Pulse teamUpdated 2 Nov 20267 min read

How to tell if Claude Code is stuck: check whether it is making progress, not whether it is busy. If it runs the same command and gets the same error after every edit, changes the same lines back and forth, or works for a long stretch with nothing new to show, it is stuck. If a question or a permission prompt is on screen, it is only waiting for you.

Below are the four signs to check at your own terminal, what to do about each, and how a lead can tell which of a team's agents need a person without asking everyone.

Stuck, waiting or frozen: three different stops

"Claude Code stuck" gets used for three situations that look alike from across the room and need different responses. Telling them apart takes about ten seconds once you know what to look at.

SituationWhat you seeWhat it needs
WaitingA question, a plan to approve, or a request to run a command or edit a file. Nothing moves until you answer.You. Usually one reply or one keypress.
StuckPlenty of activity. Edits, commands and errors keep scrolling past, but the error at the end of each round is the same one.A person with fresh context. Another retry rarely helps.
FrozenNo new output at all for a long time, and no prompt waiting for you.A look at what it last started, the network, and your plan limits.

The awkward one is the middle row. Waiting and frozen are quiet, so people notice them. A stuck agent is busy, and busy looks like work. That is why "is it doing something?" is the wrong question.

Four signs to check at your own terminal

  1. The same command keeps failing

    Scroll back over the last few rounds. If the test, build or script ends with the same error each time, with an edit in between, the edits are not reaching the cause. This is the classic AI agent stuck in a loop.

  2. The same edit is made, undone and made again

    The agent changes a line, the change breaks something else, it changes it back, and the first failure returns. Two files edited in turn, round after round, is the same pattern on a larger scale.

  3. Time passes and nothing new exists

    Ask what is different now from twenty minutes ago: a new file, a passing test, a finished step in its plan. If the honest answer is "nothing", the session is busy without progress, however much it has printed.

  4. It is waiting for permission, not stuck at all

    Before deciding anything, look at the bottom of the window. Claude Code waiting for input, or for approval to run a command, sits completely still. It looks frozen and it is the cheapest stop to clear.

When the session is frozen rather than stuck

If there is no prompt and no new output, check three things in this order. Did the agent start something that never ends on its own, such as a development server or a test runner in watch mode? Has the network dropped? And has your Claude plan window run out? A plan has a 5-hour window and a weekly window, and when one is used up the agent cannot continue until it resets. None of these is a problem with the code.

What to do once you know it is stuck

The instinct is to type "try again". It rarely works, because the agent already tried again several times. What works better:

  • Stop the run. Every extra round adds tokens and scrolls the useful error further away.
  • Read the last error yourself. You know things about your machine that the agent cannot see.
  • Look outside the code. A service that is not running, a missing credential or setting, a network call or a test configuration can fail the same way no matter what is edited.
  • Restart with a request that names the real problem, and give it the approvals it will predictably need so it does not stop at the first command.

If the same kind of loop keeps coming back, it is worth understanding why agents fall into it. Our guide to why AI agents retry the same failed fix, and how to break the cycle goes into the causes.

A Claude Code notification when waiting: useful, with one gap

You do not have to watch the terminal to catch the waiting case. Claude Code's hooks include a Notification event, and its matchers include a permission prompt and an idle prompt. A small hook can play a sound or show a desktop notification when either fires, so a Claude Code notification when waiting reaches you in another window. (Source: Anthropic's Claude Code hooks documentation, checked 2 Nov 2026.)

Notice what it cannot do. A stuck agent never asks for anything. It keeps running, so no waiting notification ever fires for it. The quiet stops come to you; the busy one does not. For that you need someone, or something, looking at whether the work is repeating.

What the team view does not tell you

  • It is a place you look. The stuck marker sits on a desk. Teams that rely on it tend to keep The Office open on a shared screen.
  • Detail is scoped. Everyone sees presence. What a stuck marker is about is shown only for yourself, the people you manage and admins.
  • A plan limit is not a stuck agent. The Office marks it separately, each developer sees their own Claude plan usage on Workspace, and Plan headroom lists who is near a limit, worst first. It covers Claude Code only.
  • It does not say whether the code is good, and it does not read keystrokes, screenshots or project source files. Session records can include excerpts of code the AI read or wrote, with secrets masked.

Questions about stuck AI sessions

How do I spot developers who are stuck in long AI sessions?

Look for repetition, not length. A two-hour session that keeps producing new files and passing tests is going well; a forty-minute one that runs the same failing command over and over is not. Across a team, Kite Pulse puts a stuck marker on the person's desk in The Office, and Work Problems lists repeated retries and failed commands. Each developer's report also shows deep sessions of 60 minutes or more and their longest session, which is a reason to ask, not a verdict.

How do I know when AI is retrying the same failed fix repeatedly?

At your own terminal, the pattern is an edit, the same command, the same error, and another edit, with nothing new in between. When you see it twice, stop the run and read the error yourself. For a team, Work Problems finds repeated retries, failed commands and error messages with fixed rules and no AI; it is an admin page by default. Failed tool calls are recorded for every supported tool except Aider.
