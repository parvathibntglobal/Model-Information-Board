Tuesday morning: a live view of AI coding agents on the meeting-room screen

Priya leads a small product team. Most of her developers spend the day directing an AI coding agent: some use Claude Code, others Cursor or Codex. Commits tell her what came out. They say nothing about an agent going round in circles.

So the team keeps The Office, a live view of every AI coding agent at its person's desk, open on the meeting-room screen. Each desk shows a person and whether they are online, away or offline, and desks are grouped by team.

Each desk can carry one marker for what needs a look, such as stuck work or a Claude plan limit. Presence is shared with everyone. Everything past presence, including what a stuck marker is about, is shown only for the viewer themselves, the people they manage and admins. The meeting-room screen is signed in as Priya, who has the Manager role, so it shows detail for her reporting line and presence only for everyone else.

Mid-morning: one desk is marked stuck

Halfway through the morning, Sam's desk shows the stuck marker. Nothing else looks wrong: Sam is online and his agent is running. In a stand-up this would not have come up until the next day.

Priya clicks the desk. Because Sam is in her reporting line, the side panel shows his current task and an "AI stuck" line saying how many times the agent hit the same problem and for how long, with plain reasons. It also shows today's tool calls and failures. It does not show what Sam typed.

Reading the session step by step

Priya opens Sam's latest session in its detailed view, the same report Sam sees of his own work. She skips the conversation and follows what the agent did: which files it touched, which commands it ran and which of them failed.

The pattern Priya reads: the agent keeps changing the code, and the same test keeps failing with the same error. That usually means the problem is not in the code being edited.

This is a retry loop. The agent treats each failure as a reason to try another edit, when the failure comes from something the edit cannot reach. Our guide to why AI agents get caught in retry loops and how to break them covers the common causes in more depth.

Why a failed command shows up as a failure

Failed tool calls are recorded for every supported tool except Aider, and command exit codes come from Claude Code, Codex and Copilot. That is what lets the step list show "failed" as a fact instead of a guess.

Before lunch: a short conversation at Sam's desk

Priya walks over and asks how the payment change is going. Sam had left the agent running while he joined a code review, expecting it to finish on its own. Together they look at the error. The tests need a local service that was not running on Sam's laptop, so no edit to the code could ever make them pass.

Sam starts the service, stops the agent's run and restarts it with a clearer request that names the real problem. The tests pass and the stuck marker clears. The whole thing took one short conversation, before the morning was lost to it, and Priya never opened Sam's messages.

Then she does the part that pays off later. If one laptop was missing the service, others might be too, so she adds a line to the project's setup notes.

When a Claude Code agent is stuck, the signs are in the steps

A Claude Code agent stuck on a task looks much the same as a stuck Cursor or Codex agent. The signs to look for in any session's steps:

  • The same command failing again and again, with edits in between.
  • The same file edited back and forth without the error changing.
  • A long session with no new result, especially when the developer has stepped away.
  • Errors that point outside the code: a missing service, a credential, a network call, a test setting.

Across a team, the same patterns are worth looking at in bulk. Work Problems uses fixed rules, with no AI, to find failed commands, error messages and repeated retries, grouped by severity with suggested actions and the most affected developers. Thresholds for spotting problems live in Detection Rules. Work Problems is an admin page by default; admins can open it to managers on Roles & Permissions.

What about an AI agent stuck notification?

Many leads want an AI agent stuck notification that comes to them, so nobody has to watch a screen. Here is what this story relies on.

  • The stuck marker in The Office is the signal Priya used. It is a place you look, which is why her team keeps it on a shared screen.
  • Needs attention is an inbox in the top bar, open to every role, for things waiting on that person.
  • Alerts and notifications come through an in-app bell, email and a daily digest, and admins choose who is told what on Notifications.

Exact "waiting for you" signals that come from Claude Code itself are in a desktop app release that has not shipped yet, so this article does not describe them. If a push alert for every stuck agent is the one thing you need, check the current feature list before you decide.

When one person runs several agents at once

Sam ran one agent. Some developers run several, plus sub-agents. Agents in parallel, on a developer's page, shows how many AI agents and sub-agents are working now and whether each is working or waiting, with a lane chart for any past day. Admins can open it for anyone; managers see it for themselves.

For a quick team-wide check without The Office, Team Overview shows who is online and who is coding right now, active time and sessions today against a typical day, and each person's current project. It refreshes every 30 seconds.

AI agent oversight that starts with a question

Good AI agent oversight looks a lot like good management of people: notice early, ask before judging, and fix the system when the same thing happens twice. The order Priya followed works with any tool:

  1. See the marker while there is still time to help.
  2. Read the steps to understand what the agent tried.
  3. Ask the developer, who knows things the steps do not.
  4. Fix the cause for everyone, not just for one laptop.

The data behind this has limits worth knowing. It comes from the AI tools' session records, folder names and repository addresses. It does not open project source files, log keystrokes, take screenshots or track websites, though session records can include excerpts of code the AI read or wrote, with secrets masked. Each person can see everything recorded about them, and who can see it, on their own Privacy page. Our privacy page explains what is read and who sees it.

Questions about seeing and helping stuck AI agents

How can I see what my team's AI agents are doing right now?

Use a view built from the AI tools' own session history rather than asking for status updates. In Kite Pulse, The Office shows a desk per person, grouped by team, with online, away or offline status and markers for stuck work or plan limits, and Team Overview shows who is online and coding right now, refreshing every 30 seconds. Detail is shown only for people in your scope; colleagues outside it appear with presence only.

How do I spot developers who are stuck in long AI sessions?

Look for the stuck marker on a person's desk in The Office, then read the session's steps for the same command or file coming back again and again. Each developer's report also lists their deep sessions (60 minutes or more) and longest session, and managers and admins can open it. A long session is not a problem on its own, so treat it as a reason to ask, not a verdict.

How do I know when AI is retrying the same failed fix repeatedly?

The session's step view shows the same command failing after each edit. Kite Pulse records failed tool calls for every supported tool except Aider, and command exit codes from Claude Code, Codex and Copilot. Across the team, Work Problems uses fixed rules, with no AI, to find failed commands, error messages and repeated retries, grouped by severity with suggested actions; it is an admin page by default.
