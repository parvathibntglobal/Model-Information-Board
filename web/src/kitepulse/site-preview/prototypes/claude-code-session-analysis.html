Claude Code Session Analysis: Learn From the Session That Went in Circles

Kite Pulse teamUpdated 2 Nov 20268 min read

Claude Code session analysis means reading back a finished session to find where it went wrong: which commands failed, what the agent kept retrying, and what your request left out. The evidence is already in the session history Claude Code keeps on your computer. Read it in order, look at the failures before the edits, and you can usually write a request that would have worked the first time.

Illustrative example, not a customer story

Two hours, one test, the same failure

Imogen asks Claude Code to fix a failing date test before the end of the day. The agent reads the parser, changes how it handles time zones, runs the tests, and the test fails. It changes the parser again. The test fails again. Two hours later the parser has been rewritten three ways and the test still fails with almost the same message.

On Monday she fixes it in ten minutes: the test reads a fixture file that was saved with the wrong date, and the agent never opened it. No change to the parser could have made the test pass.

The useful part comes after the fix. Imogen goes back to the session that went in circles and asks why it took two hours, so the next one does not. That review is what this article is about. Where Claude Code session history lives

Claude Code keeps a record of every session on your computer: your messages, the agent's replies, each tool call it made and what came back. That Claude Code session history is the raw material for any review. Commits show only what came out.

The record is long, and most of it is routine reads and edits. Read it with a few questions in hand and skip everything that does not answer them.

Signs Claude Code was stuck in a loop

When Claude Code is stuck in a loop, the session usually shows one or more of these patterns. None of them proves a loop on its own; together they are hard to miss.

What you seeWhat it usually meansWhat to change next time
The same command failing after each editThe agent is treating every failure as a reason to try another edit.Ask it to explain the failure before it changes anything.
An error message that barely changesThe edits are not reaching the cause.Name what else could be involved: config, data, environment.
One file edited back and forthThe agent has fixed on one place as the culprit.Point it at the other files the test depends on.
A file or service never looked atThe cause sits somewhere the agent did not think to check.Mention it in the request, even if you are not sure.
A failure with a non-zero exit code and no clear messageThe command itself, not the code, may be wrong.Give the exact command and how it should be run.

For the deeper causes, from missing context to tests that depend on something outside the code, see why AI agents get caught in retry loops.

A four-question review of a session that looped

  1. What was the first failure, and did it ever change? Find the first failed command and compare its error with the last one. If they match, every edit in between was a guess.
  2. Was the cause inside what the agent could edit? Read the error and the exit code. A missing file, a stopped service or a wrong setting will not yield to code changes.
  3. What did the agent never open? List the files and commands it touched. The cause is often in the gap.
  4. What did my request assume? Reread your first message. Most loops start with something you knew and did not say.

Then rewrite the request as you would send it now. In Imogen's case the difference is one sentence, and it is the sentence that matters:

Original request (example)
The date parsing test is failing. Please fix it.
Rewritten request (example)
The date parsing test is failing. Before changing any code, read the test and every fixture it loads, and tell me whether the failure is in the parser or in the test data. If the same error comes back twice, stop and report what you found.

Keep the last line as a habit: an agent told to stop after a repeated failure gives you a short session with a clear question.

Choosing a Claude Code session analyzer

There are three practical ways to do this review. Which one fits depends on how often you want to do it, and whether anyone besides you needs the answer.

ApproachGood forWeak at
Read the raw history yourselfA one-off look at one session, with nothing to install.Long sessions, spotting patterns across weeks, and any tool other than Claude Code.
A personal Claude Code session history viewerBrowsing and searching your own sessions on one computer.Sessions from other machines or other AI tools, and anything a team needs to see together.
A team platform that reads session historyYour sessions from every computer and tool in one place, plus team-wide patterns.It needs a server and an admin to set it up, which is more than a solo developer may want.

If you work alone with one tool, a local viewer may be all you need. The team option earns its setup when several people hit the same walls, or when you use more than one AI tool and want one place to look back.

When it is not just your session

Imogen's loop came from one bad fixture. If the same test data had tripped three people, the fix belongs to the team, not to three better prompts. Work Problems uses fixed rules, with no AI, to find failed commands, error messages and repeated retries across the team, grouped by severity with suggested actions and the most affected developers.

Work Problems is an admin page by default, so as a developer you may not see it. Admins can open it to other roles on Roles & Permissions. If you suspect a shared cause, the quickest route is often to tell whoever can see it. For a wider view of what developers get from the console, see what the console gives developers.

Be clear about who sees your sessions, too. A manager sees the same report you see for people in their reporting line, and admins see everyone, without your private prompt statistics. A review of your own loop is something you can do privately; the session itself is not hidden from them.

Questions about Claude Code session analysis

How do I know when AI is retrying the same failed fix repeatedly?

Look at the failures in order, not at the edits. If the same command fails after every change and the error text barely moves, the agent is retrying one fix in different forms. In Kite Pulse, failed tool calls are recorded for every supported tool except Aider and command exit codes for Claude Code, Codex and Copilot, so a session's detailed view in My Sessions shows those failures as recorded facts. Across a team, Work Problems uses fixed rules to find repeated retries; it is an admin page by default.

Can my manager see my Claude Code session history?

In Kite Pulse, a manager sees the same report you see for people in their reporting line, and admins see everyone, but your private prompt statistics are shown only to you. Secrets are masked on your computer before upload and again on the server. Your Privacy page lists every data point collected about you, whether it is on, and who can see it.

Does Claude Code session analysis need an AI service?

No, not for the review itself. Collection, My Sessions, the recorded failures and exit codes, and Work Problems all run without any AI service, on the server your team runs. AI labelling, which can tag the type of work and whether a session succeeded, is optional and stays off until an admin sets it up.
