Claude Code Agent Features Usage: Invest in the Tooling Your Team Actually Uses

Kite Pulse teamUpdated 2 Nov 20268 min read

Claude Code agent features usage is the record of which agent features your developers' sessions really use: sub-agents, background commands, plan mode, worktrees, MCP tools and the rest, counted by session and by developer. It is the most reliable guide to where platform and developer-experience effort will pay off, because it comes from what the tool recorded, not from what people remember or what is installed. Pair it with the models and settings people choose, and you can decide what to standardise, document or build next.

Why usage should steer developer-experience spending

Platform and developer-experience leads have more things they could build than time to build them. A shared MCP server for the internal ticket system. A house guide to plan mode. A worktree setup so people can run agents side by side. A set of team skills. Each one is a reasonable bet, and each one costs weeks.

The usual way to choose is to ask around, or to look at what is configured. A list of MCP servers installed across the team tells you what is available on people's machines. It does not tell you whether anyone calls those tools in a working session, or whether the one person who set a server up is also the only person using it. Configuration is intent. Sessions are behaviour.

Usage data shows who already depends on a feature and which teams do not use it at all. The first group needs reliability and documentation. The second might need training, or might have a good reason to skip it.

What each Claude Code agent feature tells you

Each Claude Code agent feature points to a different kind of investment. The table is general guidance for reading usage, not a scorecard.

Feature in useWhat steady use suggestsWhat low use might mean
Sub-agentsPeople split larger jobs into parallel parts. Shared sub-agent definitions and clear guidance on when to use them will be read.Work is mostly small, or people do not know when a sub-agent helps.
Background commandsLong builds, test runs or servers run while the agent keeps working. Fast, reliable local tooling matters here.Builds are short, or the pattern is unfamiliar.
Plan modePeople agree an approach before the agent edits files. A shared planning checklist may be worth writing.Tasks are routine, or people go straight to edits on larger work too.
WorktreesSeveral agents work on one repository at once. Setup scripts and clean-up habits for worktrees pay off.One agent per repository is the norm.
MCP toolsAgents reach internal systems through MCP. Those servers are now part of how work gets done and need an owner.Servers were installed but are not part of daily work, or are hard to set up.

Low use is not a verdict. A team on a small, stable codebase may rarely need worktrees. The useful question is whether the pattern matches the work.

Four ways to find out what the team uses

Quick

Ask the team

Good for why people use a feature and what gets in the way. Weak for counts: people underestimate habits and overestimate experiments, and the answers cannot be repeated next quarter.

Inventory

Look at what is configured

Shows what is installed or set up. It cannot separate a server used every day from one tried once, and it says nothing about plan mode or sub-agents.

Per vendor

Vendor dashboards

Accurate for that vendor's product as far as each one goes. A team on several assistants gets several partial views, and feature-level detail varies.

Sessions

Session history

Reads what each session recorded on the developer's computer: features, tools and models, linked to a person and a project, with nothing for anyone to log.

Session history tells you where to look; a short conversation tells you why. For a broader view of how session data fits beside other engineering measures, read our guide to AI coding analytics for teams.

MCP tool usage analytics: from installed to relied on

MCP tool usage analytics answers a narrow question that matters a great deal to platform teams: which internal systems do agents actually reach, and who depends on them? Once agents call a server in everyday work, that server has users. It needs someone to keep it running, a place to report problems and documentation for people who join later.

Counting MCP tool use by session and by developer shows whether use is spread across teams or concentrated in a few people. Concentrated use is a hint that something works well for one group and has not travelled, often because setup is hard or nobody wrote it down.

Model usage by developer and AI model adoption tracking

Features are half the picture. The other half is which models people choose and how they configure them. Model usage by developer shows whether a team has settled on a default or whether every person picks differently. AI model adoption tracking shows how quickly a new model is picked up, and which projects still rely on an older one.

For Claude Code, the effort-level and speed settings people run with are worth reading too. If most sessions on a project use one setting and a few use another, that is a good prompt for a short conversation about what works, and perhaps a team default.

Model names come from what each tool records. For Claude Code, Codex, Gemini CLI, Cline, Roo Code, Kilo Code, OpenCode and Aider the model is recorded. Cursor records a model name only when one model served the whole chat, and GitHub Copilot Chat in VS Code only when it was recorded, so read those two as partial.

An illustrative example

Illustrative example, not a customer case

A platform lead is deciding between two projects for the quarter: a second MCP server for the deployment system, or better documentation for the existing one that connects to the ticket system. The Agent features tab shows MCP tools used in sessions on two teams and almost nowhere else. A conversation with a third team reveals they tried the ticket server once and gave up on setup.

The lead writes the setup guide first. Separately, Skill Candidates shows the same release-notes workflow repeating across several developers, so a draft skill goes to review. The second server waits for next quarter, when there is evidence the first one travelled.

What this view does not show

What it counts

  • Claude Code agent features used, by session and developer
  • Models per developer and per project, and adoption over time
  • Claude Code effort-level and speed settings
  • Repeated workflows that could become a skill

What it does not count

  • Agent features in tools other than Claude Code
  • Whether a feature made the work better or faster
  • Activity from developers who have not confirmed their projects
  • AI tools outside the ten supported ones

Usage is not a measure of value, and this is not a code-quality tool. If your question is delivery speed from git and tickets, a git-based analytics tool is the better fit for that part.

Questions about Claude Code agent features usage

Which Claude Code features (sub-agents, plan mode, MCP tools) does my team use?

Read it from the Claude Code session history rather than asking around, because each session records the agent features it used. In Kite Pulse, the Agent features tab of Team AI Usage shows which Claude Code agent features sessions used, including sub-agents, background commands, plan mode, worktrees and MCP tools, by session and by developer. It covers Claude Code only; other tools do not appear on that tab.

How can I track which AI models (Opus, Sonnet, GPT) my team uses?

Use the model name each AI session records, counted per developer and over time. Kite Pulse's Models tab shows developers per model, model adoption over time and models by project, across the ten supported tools, so Claude models from Claude Code and GPT models from Codex sit in one view. Cursor records a model name only when one model served the whole chat, and GitHub Copilot Chat in VS Code only when it was recorded.

Can I see which AI models are being used and how frequently?

Yes, for the tools that record a model name. Team AI Usage shows token use per developer, tool, model, project and day for any period, and the Models tab shows how many developers use each model and how that changes over time. For Claude Code it also shows the effort-level and speed settings in use.
