Reading an Agent's Body Language: How to Visualize AI Agents Working

Kite Pulse teamUpdated 30 Oct 20268 min read

To visualize AI agents working across a team, you need a few plain states for each agent: working, waiting for its developer, waiting for permission, stuck, or stopped at a plan limit. Each one asks for a different response, and most of them are invisible from outside the developer's terminal.

This article explains what each state usually means, what to do about it, and the ways a team can see those states without asking every developer in turn.

Why it is hard to see what AI agents are doing right now

An AI coding agent works inside one person's terminal or editor, on one computer. It reads files, runs commands, edits code and sometimes starts sub-agents of its own. All of that scrolls past in a window only its developer is looking at, and often not even them: the point of an agent is that you can hand it a task and turn to something else.

So the question a lead most wants answered, "is the work moving?", has no obvious place to look. Commits arrive late, and a stand-up gives a summary from memory once a day. And a developer running two or three agents at once may not know which one has been sitting idle for the last twenty minutes.

If you want to see what AI agents are doing right now, the agents' own session records are the honest source. Coding assistants such as Claude Code, Codex and Cursor already keep them on each developer's computer as they work. Read those, and an agent's state becomes something you can look at instead of something you have to ask about.

Five states, and what each one asks of you

Think of these as an agent's body language. None of them tells you whether the code is good. Each tells you whether the work is moving, and if it is not, whose move it is.

StateWhat it usually meansWhose move
WorkingThe agent is taking steps: reading, editing, running commands, or supervising its sub-agents.Nobody's. Leave it alone.
Waiting for the developerThe agent has replied or asked a question and is holding until its person answers.The developer. Often they have simply moved on to something else.
Waiting for permissionThe agent wants to run a command or change a file and needs someone to approve it.The developer. This is the cheapest stall to clear: one keypress.
StuckThe agent keeps hitting the same problem, often the same failing command, without getting further.A person, with fresh context. More retries rarely help.
At a plan limitThe developer's Claude plan window is used up, so the agent cannot continue until it resets.Whoever plans the work. Nothing in the code is wrong.

The table also shows why one green or red light per person is not enough. A waiting agent and a stuck agent both look "not working" from a distance, and they need opposite responses: one needs a reply in ten seconds, the other needs someone to sit down and think.

Claude Code waiting for input: the quiet stall

The most common lost time with an agent is not failure. It is waiting. The agent finishes a step, asks "shall I run the migration?", and the developer is in a meeting or deep in another window. The agent costs nothing while it waits, which is exactly why nobody notices. The task just takes the afternoon instead of the hour.

Two kinds of waiting are worth telling apart. Claude Code waiting for input after a reply is a conversation pause; the developer decides what comes next. Waiting for permission is narrower: the agent already knows what it wants to do and needs a yes. When people run several agents in parallel, permission waits pile up first, because each agent asks at its own moment.

What helps:

  • Before handing off a long task, give the agent the approvals it will predictably need, so it does not stop at the first command.
  • Treat a waiting agent as a reminder, never as a mistake. It usually means the person has other work.

When a Claude Code agent is stuck: reading the signs

A Claude Code agent stuck on a problem rarely looks stuck from the inside. It is busy. It runs the test, reads the error, changes a line and runs the test again. Tokens keep flowing and the work does not move. That is why "is it active?" is the wrong question and "is it making progress?" is the right one.

The signs are mechanical, which makes them easy to spot in a session record and hard to spot in a scrolling terminal:

  • the same command failing again and again, with the same error;
  • the same file edited back and forth;
  • a long stretch of activity with no new file, test or commit at the end of it.

We cover the mechanics of those cycles, and how to break them, in our guide to AI retry loops. The short version: a person with fresh context usually ends a stuck stretch faster than another retry, so the value is in noticing early.

In Kite Pulse, Work Problems finds failed commands, error messages and repeated retries with fixed rules and no AI, grouped by severity with suggested actions. In The Office, a stuck agent gets a marker on its desk, and for people in your scope the desk says how many times the agent hit the same problem and for how long, with plain reasons.

The agent that stops for reasons outside the code

Some stops have nothing to do with the task. A Claude plan has a 5-hour window, a weekly window and a weekly window per model. When one is used up, the agent cannot continue until that window resets. From outside it looks like an agent that went quiet.

This state is worth seeing before it arrives. In Kite Pulse, a reading of 80% or more counts as "near" and 100% as "at limit", and The Office marks plan limits on the desk. Plan headroom lists who is close to a Claude plan limit, worst first. It covers Claude Code only; other tools show "Not reported by this tool".

Three ways to see what agents are doing

The right way to watch agents depends on how many people and agents are involved.

ApproachWhat you seeWhat you missFits when
Ask, or look at the terminalExactly what the agent is doing, in full.Everything you did not ask about, and anything between check-ins.One developer, or a pair working side by side.
Each tool's own interfaceIts own sessions, in that tool's terms.Other tools, other people, and any view across the team.A team on one tool that needs no shared picture.
A team view built from session historyState, presence and markers for many people and tools at once.The conversation itself, and anything the tools do not record.Several people running agents, often in parallel, across tools.

If you work alone with one agent, your terminal is enough, and adding a dashboard would be ceremony. The third approach earns its place when a lead needs to know which of a dozen agents need a person, without interrupting a dozen people to find out.

What the signals do not tell you

A state is a description of what an agent did, and nothing more. Read it with that in mind:

  • Waiting is not idleness. A developer with a waiting agent is usually doing other work, often reviewing what an agent produced earlier.
  • Working is not progress. A stuck agent is busy too. Look at whether the same problem keeps coming back.
  • Offline is not absent. People step away, travel and take leave. A quiet desk on a leave day says nothing about the work.
  • None of it says whether the code is good. That still takes a review.

Used this way, a view of agent state replaces a round of "how is it going?" messages with a quick look.
